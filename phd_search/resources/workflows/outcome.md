# /outcome — application tracking, references and follow-ups

Read `docs/cli.md` and `docs/application-review.md`. Keep an auditable event history; a draft, sent message, submitted application and outcome are distinct facts.

1. Identify the application by exact opportunity/reference/ID; ask on ambiguity. Read current status and original/submitted materials. Preserve earlier events and distinguish event date from recording date.
2. Record only user-confirmed actual status using `./roost application status APP_ID STATUS --on YYYY-MM-DD --note SOURCE`. Supported states: preparing, drafted, submitted, assessment, interview, waitlisted, offer, accepted, declined, rejected, withdrawn, expired. Check allowed transitions. Offer is not acceptance; an invitation is not a completed interview; no response is not rejection.
3. A submitted transition requires reviewed materials and archives their exact source/profile/documents/manifest. If an application was submitted externally, first import the actual submitted materials rather than generating retrospective achievements. Missing eligibility may be explicitly acknowledged with `--allow-unknown`; document failures remain blocking.
4. Record a scheduled interview, assessment deadline, feedback, user-sent contact or follow-up as a separate `application event` with a source note. Scheduled events require an offset-aware ISO timestamp. Keep objective event facts separate from the candidate's interpretation of a response.
5. Manage references with `application referees APP_ID --file referees.json`. Record confirmed permission separately from name/email; track requested, due and received dates and the submission route. Never fabricate a referee's consent or write/send a recommendation in their name. Request drafts and reminder drafts remain local unless the user instructs a send.
6. `/outcome followup` maps to `./roost followup` (optionally `--draft`). It uses recorded submission/contact history, a configurable interval and at most two recorded follow-ups. Re-running draft generation preserves the existing file. Read the institution's own contact/timeline instructions first; do not propose a reminder where they forbid one or an actual timeline has not elapsed.
7. Personalise follow-up and thank-you prose using only actual submitted claims and confirmed interview discussion. Keep it concise and channel-appropriate. Never invent a deadline, another offer or urgency. Mark `followup_sent` only after the user confirms it was actually sent.
8. After several actual outcomes, summarise observed funnel counts by route/source/stage and recurring feedback. Small, selected samples do not establish success probabilities or causal effects. Propose profile/rubric improvements from evidence; do not silently change weights or erase rejected cases.
9. Regenerate dashboard, tracker CSV and calendar as needed. Return updated state, paths and concrete next dates. No external messaging or form submission occurs in the tracking commands.
